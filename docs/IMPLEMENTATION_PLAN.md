# BLOCKS full-stack: audit and implementation plan

Written at the start of the full-stack work (2026-10-09) and updated as each stage
finishes. Status words are used strictly:

| Word | Meaning |
|---|---|
| **Verified** | Code, integration and an automated test that was actually run |
| **Mocked** | Works, but a development stand-in plays the part of a real provider |
| **Partial** | Some of the behaviour exists; the gap is listed |
| **Needs credentials** | Needs a real provider account (SMS, e-mail, KYC, bank, S3...) |
| **Needs review** | Needs legal / compliance sign-off before real use |
| **Needs infrastructure** | Needs production infrastructure (CDN, WAF, HA Postgres...) |

## 3. Principles that apply to every stage

1. The server is the authority. The client may preview a rule; it never decides reach
   level, verification, balance or eligibility.
2. Every external provider (SMS, e-mail, push, KYC, bank, payout, object storage,
   transcoder, moderation) sits behind an interface with a clearly labelled development
   implementation.
3. Money is `NUMERIC(18,2)` and moves only through an append-only ledger inside a
   transaction, with a unique idempotency key.
4. Sensitive identifiers are encrypted at rest, masked everywhere they are shown, and
   never logged.
5. A feature is called complete only when its code, its integration and a test that
   actually ran all exist.
